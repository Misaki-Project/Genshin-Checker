# Codex向けオフラインデバッグ環境 設計

## 概要

Genshin Checkerに、Codexと開発者が同じ手順で安全に変更を検証できるオフラインデバッグ環境を追加する。

検証では実際のHoYoLab API、Windowsレジストリ、既存のユーザーデータを使用しない。ローカルとGitHub Actionsは同一のPowerShellスクリプトを実行し、環境差による見落としを防ぐ。あわせて既存のコンパイラ警告を整理し、Releaseビルドを警告0件にする。

## 目標

- Codexが単一コマンドでrestore、build、testを実行できる。
- テストがネットワークや個人データに依存せず、毎回同じ結果になる。
- GitHub Actionsがローカルと同じ検証経路を使用する。
- Releaseビルドの警告を0件にし、新しい問題を発見しやすくする。
- 既存アプリの本番動作とデータ形式を維持する。

## 対象外

- 新旧UIの統合や大規模なMVVM移行
- Generic HostやDIコンテナを使ったアプリ全体の再構築
- 実アカウントを使用する結合テスト
- GUI操作、Windows通知、ゲームプロセス監視のE2Eテスト
- 今回のテスト容易性に関係しない機能リファクタリング

## 現状

- アプリは`net8.0-windows10.0.22621.0`を対象としている。
- `.vscode/launch.json`は以前の.NET 6出力先と存在しないDLL名を参照している。
- `.vscode`自体が`.gitignore`対象で、正しい起動設定を共有できない。
- GitHub Actionsは.NET 6をセットアップしており、現在のプロジェクトと一致しない。
- テストプロジェクトが存在しない。
- Debugビルドは成功するが、Modelの未初期化、生成リソースの命名、nullable、非推奨APIなどを中心に422件の警告が出る。
- HTTP、レジストリ、AppData保存、現在時刻への依存が静的実装に結び付いている。

## アーキテクチャ

検証の正式な入口を`scripts/verify.ps1`に統一する。

```text
Codex / 開発者 --+
                  +--> scripts/verify.ps1
GitHub Actions ---+       +--> restore / Release build
                          +--> offline unit tests
                          +--> test result output
```

テストプロジェクトは`tests/GenshinChecker.Tests`に配置する。既存コードにはHTTP、ユーザーデータ保存、時刻、必要最小限のレジストリアクセスを差し替えるための薄い境界を追加する。本番アダプターは従来と同じ外部資源を使用し、テストアダプターは固定応答と一時領域だけを使用する。

依存性注入フレームワークは導入しない。コンストラクター引数、内部プロパティ、または小さなインターフェースを使い、対象クラス単位で依存を渡す。

## コンポーネント

### 検証スクリプト

`scripts/verify.ps1`は次を順に実行し、いずれかが失敗した場合は非ゼロで終了する。

1. NuGet restore
2. Release build
3. テスト実行とTRX生成
4. 結果の短い要約表示

引数でrestoreを省略できるようにし、GitHub Actionsのキャッシュや反復実行に対応する。スクリプトは秘密情報を要求せず、対話入力も行わない。

### テストプロジェクト

xUnitを使用し、テストプロジェクト自身の警告はエラーとして扱う。フィクスチャは`tests/GenshinChecker.Tests/Fixtures`以下に置き、架空のUIDとCookieだけを使用する。テストごとに一時ディレクトリを作成し、終了時に削除する。

テストアセンブリから本体のinternal要素へ必要最小限のアクセスを許可する。公開APIをテスト専用に増やさない。

### HTTP境界

HTTP取得を小さな抽象へ分離する。本番実装は現在のヘッダー生成とレスポンス処理を維持する。テスト実装は登録済みの固定応答だけを返し、未登録URLへの要求を失敗させる。

テストプロセスから実ネットワークへフォールバックする経路は用意しない。

### ユーザーデータ境界

保存ルートを外部から指定できるストアを導入する。本番実装の既定ルートは現在と同じApplication Data配下とする。テストでは専用の一時ディレクトリを渡す。

既存の非圧縮Debugデータと圧縮Releaseデータの形式は維持する。保存と読み込みの核となる処理は構成から独立させ、両形式をテストできるようにする。

### 時刻境界

現在時刻を読む処理には小さなクロック抽象を導入する。固定UTC時刻を渡し、デイリー更新直前・直後や週次更新を決定的にテストする。Unix時刻変換のような純粋処理は直接テストする。

### レジストリ境界

今回のテスト対象が必要とする読み書きだけを抽象化する。テストではインメモリ実装を使用し、`Microsoft.Win32.Registry.CurrentUser`へ一切アクセスしない。レジストリ全体の再設計は行わない。

## データフロー

API系テストでは、JSONフィクスチャをHTTPテストアダプターへ登録し、対象サービスへ注入する。対象サービスは本番と同じJSON変換とエラー判定を実行し、Modelまたは既存例外を返す。

保存系テストでは、テストケースが一時ルートを作成し、ストアへ文字列を保存する。同じストアで読み戻して内容を比較し、テスト終了時に一時ルートを削除する。

時刻系テストでは、固定クロックを変換処理へ渡し、タイムゾーン、毎日4時の更新境界、月曜の週次更新境界を検証する。

## エラー処理

- 不正JSONは現在の`InvalidDataException`契約を維持する。
- HoYoLabの非ゼロ`retcode`は既存のAPI例外へ変換する。
- HTTP失敗は固定レスポンスで再現し、既存の戻り値または例外契約を確認する。
- 存在しない保存ファイルと壊れた圧縮データを別々に検証する。
- テストで未登録のURL、実レジストリ、既存AppDataへアクセスしようとした場合は直ちに失敗する。
- 既存コードが例外を握りつぶしている箇所は、挙動変更が必要なら先に特性テストを追加する。

## 初期テスト範囲

### JSONと変換

- 正常JSONのデシリアライズ
- 不正JSONと`null`相当JSON
- JSONの整形
- Unix時刻とUTCの相互変換
- サーバー名とUTCオフセット
- デイリー更新の直前・直後
- 次回週次更新

### ユーザーデータ

- 非圧縮データの保存と読み戻し
- 圧縮データの保存と読み戻し
- 相対パスを指定した場合の保存ルート
- 存在しないファイル
- 壊れた圧縮データ
- 保存先ディレクトリの自動作成

### API応答

- 正常応答
- HoYoLabの非ゼロ`retcode`
- HTTPエラー相当
- 壊れたJSON
- 認証情報がない場合
- 未登録URLで外部通信せず失敗すること

## 警告整理

Releaseビルドを警告0件にする。修正は次の規則で行う。

- Newtonsoft.Jsonが設定する必須参照型は、serializer-ownedであることが分かる初期化を行う。
- 欠損が正常な状態であるプロパティだけをnullableにする。
- 空コレクションが正当な既定値である場合だけ空で初期化する。
- API境界で必須データを検証し、不正応答を空値として処理しない。
- 手書きコードの命名、重複using、未使用メンバー、nullable警告は直接修正する。
- `.Designer.cs`などの生成コードは直接編集しない。
- リソース名由来で互換性への影響が大きい警告は、対象コードが生成物であることを確認し、理由をプロジェクト設定へ記録したうえで警告番号を限定して抑制する。
- 非推奨APIの置換やnull処理が挙動を変え得る場合は、修正前に特性テストを追加する。

警告抑制をModel全体やプロジェクト全体へ広く適用して、実際のnullable問題を隠すことは禁止する。

## GitHub Actions

既存workflowを現在のプロジェクトへ合わせて更新する。

- Windows runnerを使用する。
- .NET 8 SDKをセットアップする。
- restore後に`scripts/verify.ps1`を実行する。
- 基本検証はRelease構成の1ジョブとし、同じ検証をDebug/Releaseで重複実行しない。
- 成否にかかわらずTRXと必要な診断ログをアップロードする。
- テストやビルドが失敗した場合、workflowも失敗させる。

ローカルではworkflowと同じスクリプトを実行する。workflowファイルの変更後、公開が許可された段階でブランチをGitHubへpushし、実際のActions結果が成功することを完了条件とする。push前のローカル実装完了と、push後のリモートCI確認は権限上の別工程として扱う。

CIがテスト失敗を検出できることを確かめるため、実装中にテストを一時的に失敗させて検証スクリプトが非ゼロ終了することを確認する。その一時変更はコミットしない。リモートCIでも同じ破壊確認を行う場合は、専用の一時ブランチまたは追跡対象外の手動workflow入力を用い、mainへ故意の失敗を入れない。

## 開発者・Codex向けガイド

リポジトリ内の開発ガイドへ次を記載する。

- 必要な.NET SDKとWindows要件
- 初回セットアップ
- 正式な検証コマンド
- 特定テストだけを実行する方法
- テストが実API、実Cookie、実UIDを使用してはいけないこと
- 変更後に検証スクリプトを実行すること
- GUIを手動起動する場合の共有デバッグ設定
- GitHub Actions失敗時にTRXとログを確認する方法

共有するVS Code設定は.NET 8の実際の出力先と実行ファイル名を参照させる。個人用設定だけを除外できるよう`.gitignore`を調整する。

## 完了条件

- クリーンな作業コピーで`scripts/verify.ps1`が成功する。
- Releaseビルドが0エラー、0警告で完了する。
- すべてのテストが実API、実レジストリ、既存ユーザーデータへ触れずに成功する。
- テスト中の未登録ネットワークアクセスが失敗する。
- 検証スクリプトが失敗するテストを正しく非ゼロ終了として報告する。
- ローカルとGitHub Actionsが同じ検証スクリプトを使用する。
- pushが許可された後、対象コミットのGitHub Actionsが成功する。
- 開発ガイドだけを読んだCodexまたは開発者が検証を再現できる。
- 本番の保存先、保存形式、API契約、画面挙動に意図しない変更がない。
